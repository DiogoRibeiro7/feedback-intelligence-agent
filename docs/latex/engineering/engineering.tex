\chapter{Engineering Overview}
\label{ch:engineering-overview}

This part answers a single question: \emph{how is this software developed,
verified, built, reproduced, packaged, and released?} It documents controls
that exist in the repository. Anything that would be advisable but is absent is
confined to \cref{ch:improvements} and is never presented as an existing
capability.

\section{The lifecycle as implemented}

\input{diagrams/engineering/lifecycle}

Six checks run on every push and pull request to \texttt{main} or
\texttt{develop}, in this order, inside a single \texttt{quality} job repeated
across three Python versions: lint, format check, type check, tests with a
coverage floor, the deterministic demo, and the package build. The job fails at
the first failing step, so the order is also a triage order --- style problems
surface before type problems, which surface before test failures.

Four further workflows run independently, on their own triggers: CodeQL
analysis, dependency review on pull requests, a container build with a smoke
test, and a frontend build with an npm audit. A fifth runs on release tags.

\section{Interfaces a contributor uses}

\begin{description}[nosep]
  \item[\texttt{make quality}] lint, type check, tests --- the fast local loop.
  \item[\texttt{make ci}] lint, format check, type check, coverage, build ---
    the closest local equivalent of the CI job.
  \item[\texttt{make docs}] regenerate this manual's LaTeX sources and validate
    them.
  \item[\texttt{make demo}] the offline end-to-end demonstration that CI also
    runs.
\end{description}

The full generated target list is in \cref{ch:build}.
