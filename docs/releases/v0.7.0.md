# v0.7.0 upgrade notes

This release adds API-key tenant authorization, tenant record ingestion, and
automatic retrieval snapshot refresh across cooperating API workers. Optional
Qdrant snapshot caching avoids downloading an unchanged collection for each
request. Python 3.10, 3.11, and 3.12 remain supported, and the default local demo
still works without API keys or external services.

## Upgrading from v0.6.0

Existing v0.6.0 JSON indexes and Qdrant collections require no format migration.
Keep a backup of the index or collection and the source records before changing
deployment settings. Upgrades from earlier versions must also follow the
[v0.6.0 migration notes](v0.6.0.md), particularly the source identifier changes.

Install the selected package version and retain the `qdrant` extra if using that
backend. Restart API workers to load the new code and configuration. The default
empty tenant policy preserves global role access. JSON API workers now refresh
changed indexes automatically; coordinated Qdrant ingestion remains opt-in.

## Bind API keys to tenants

Enable API authentication and configure the reader, writer, and admin keys as
described in the [API access controls](../../README.md#api-access-control).
`FEEDBACK_AGENT_API_TENANT_BINDINGS` maps the actual configured key values to
tenant IDs. For the README's local demonstration keys:

```bash
export FEEDBACK_AGENT_API_TENANT_BINDINGS='{"read-local":"acme","write-local":"acme"}'
```

Replace demonstration keys with generated secrets for a deployment, keep the
mapping with those secrets, and restart workers after changes. With a nonempty
map, every configured non-admin key needs a binding. An unbound admin retains
global access; binding the admin also restricts it to that tenant. Invalid
nonempty policies fail protected requests with a generic configuration error.

Bound keys inherit their tenant on queries, streams, chat, reports, human
feedback, review queues, and summaries. Explicit foreign tenants return `403`;
foreign resource IDs return `404`. Global index rebuilds and ingestion-job
operations require an unrestricted admin. Tenant-bound writers and admins use
the new record endpoint instead.

Binding or reassigning an existing key makes its old unscoped or foreign
conversation histories unavailable through the API. Start a new conversation;
the service does not relabel historical resources. Empty bindings still allow
authenticated callers to select any tenant. CLI access remains local/global.
Downgrading to v0.6.0 removes these tenant authorization controls, so keep
tenant-facing traffic disabled if a rollback is necessary.

## Ingest records without replacing other tenants

`POST /ingestion/records` accepts 1–1,000 feedback records from a tenant-bound
writer or admin, an unrestricted admin, or an unauthenticated local deployment.
Bound callers may omit the batch and record tenant fields. Explicit tenant
values must match; the entire batch is rejected before writing if any do not.
An unrestricted caller can select a batch `tenant_id`, defaulting to `default`.
See the [request example and response counts](../../README.md#tenant-record-ingestion).

The endpoint validates records, keeps the last occurrence of repeated IDs,
redacts PII, and replaces only the selected tenant's source records. Retrying a
batch replaces the same records. The response contains batch counts without
global index totals or server paths. Index path overrides are not accepted.

Ingested records persist in the index or collection, not in the original CSV.
Retain the submitted batches or update the source dataset before a full rebuild;
rebuilding from an older CSV would discard records added through this endpoint.

## JSON API workers refresh automatically

Workers notice changes to their configured JSON index before query, streaming,
and chat requests, including changes made by other workers, CLI updates, and
ingestion jobs. Retrieval and dataset tools refresh together; in-flight answers
keep their selected snapshot and provider state survives the refresh. Cooperating
writers must use the shared atomic persistence and locking helpers.

A missing or invalid committed index now returns `503` on new answer requests.
Restore a valid index to recover on the next request; refresh never rebuilds
silently from CSV. The first request after an update pays the reload cost and
can wait up to 60 seconds for the writer lock. `/health` and `/ready` still report
process/startup status, not the availability of the latest snapshot. Standalone
agents built with `build_agent()` retain their existing behavior.

## Enable coordinated Qdrant ingestion

All API workers and external writers serving a collection must share one lock
path on a filesystem that supports local process locks:

```bash
export FEEDBACK_AGENT_VECTOR_STORE=qdrant
export FEEDBACK_AGENT_QDRANT_INGESTION_LOCK_PATH=/shared/feedback/qdrant-records
export FEEDBACK_AGENT_QDRANT_SNAPSHOT_TTL_SECONDS=0
```

Configure the existing Qdrant URL and collection settings for your deployment.
Without the lock-path setting, Qdrant keeps its existing retrieval behavior and
record ingestion returns `409`. Coordinated mode downloads the full collection's
chunks and vectors into each worker's memory on refresh, then runs retrieval and
tools over one immutable local snapshot. Use it only for collections that fit
comfortably in worker memory.

Qdrant upsert and obsolete-chunk deletion remain separate operations. A failure
can leave partial updates and returns `500`; retry the identical batch to finish
the replacement. Subsequent reads load the actual persisted state. Startup can
still seed an empty collection from the configured dataset; request-time refresh
does not rebuild empty collections.

## Opt into Qdrant snapshot caching

Keep the default TTL of `0` during rollout. Upgrade every API worker and make
external writers hold `qdrant_write_lock()` from
`feedback_intelligence_agent.qdrant_coordination` throughout each complete update.
Then set `FEEDBACK_AGENT_QDRANT_SNAPSHOT_TTL_SECONDS` to a value up to `3600`
(for example, `5`) and restart workers. Positive values require coordinated
Qdrant mode.

Cache hits check the shared generation file without calling Qdrant. Cooperating
writes invalidate caches before remote mutation, including when writes fail
partway. Older writers using only `index_write_lock()` become visible to cached
workers at TTL expiry. A valid cache may serve during a Qdrant outage until it
expires or is invalidated; refresh failures return `503` without extending its
lifetime. Ingestion always reads persisted data before preparing an update.

Retain the shared `*.lock` files while workers run. The sibling
`<lock-path>.revision.json` contains only a version and UUID generation. A missing
marker triggers reload; a malformed marker blocks queries and ingestion until
repaired or removed under `index_write_lock()`. See the
[cache operations guide](../../README.md#optional-qdrant-snapshot-cache).

This coordination uses local process locks. Independent hosts, distributed
writer coordination, and remote transactional replacement remain unsupported.
Direct Qdrant writes outside the shared lock can make paginated snapshots
inconsistent, even with a zero cache TTL.
