# v0.6.0 upgrade notes

This release improves tenant-scoped retrieval and aggregation, authenticated
conversation ownership, JSON index durability, and dependency security. Python
3.10, 3.11, and 3.12 remain supported. The local demo still needs no API keys.

## Highlights

- Retrieval applies metadata filters before limiting candidates. Sentiment and
  issue-cluster tools use the same filters across all matching indexed records.
- Authenticated conversation history belongs to the API key that created it.
  Follow-ups retain the conversation's tenant scope.
- JSON index writes are atomic; cooperating writers serialize incremental
  updates and startup initialization through a shared file lock.
- The MLflow extra uses the tracking client with SQLite support. The lockfile
  removes unused dependencies and updates affected retained packages.
- Release checks keep Python, frontend, citation, and Zenodo metadata aligned.

## Indexes and source identifiers

Back up existing indexes and retain the original feedback dataset before
upgrading. Source identifiers now escape tenant and feedback ID components to
avoid collisions. JSON indexes record `source_id_version: 2`; loading an older
index migrates identifiers in memory, and an explicit save persists them.
To write a separate migrated copy:

```python
from feedback_intelligence_agent.vector_store import InMemoryVectorStore

store = InMemoryVectorStore.load(".artifacts/vector_store.json")
store.save(".artifacts/vector_store.v2.json")
```

Inconsistent legacy identity metadata fails validation. Records already lost to
an earlier ID collision must be reingested from the original data. Existing
saved reports retain their historical citation identifiers.

Qdrant collections whose legacy identifiers need escaping must be rebuilt in a
new collection. Set `FEEDBACK_AGENT_QDRANT_COLLECTION` to a new name and
`FEEDBACK_AGENT_DATA_PATH` to the original dataset, then run a query to initialize
the new collection. Retain the old collection until the rebuilt data is verified.

The configured JSON index directory must be writable for temporary snapshots
and the sibling `<index>.lock` file. Use `update-index` for concurrent incremental
ingestion. Existing in-memory retrievers require rebuilding or restarting to
load an updated on-disk snapshot.

## Authenticated conversations

Authenticated callers omit `conversation_id` when starting a conversation and
use the returned ID for follow-ups. Unknown IDs and IDs owned by another API key
return the same 404, including for admin keys.

Existing unowned histories remain in the conversation root for local/CLI use.
They are not automatically assigned to an authenticated key; start a new session
after enabling authentication. New authenticated histories live under
`authenticated/<principal-digest>/` beneath the configured conversation root.
Sharing a key shares history, changing its role preserves identity, and rotating
the key creates a new namespace.

A follow-up inherits the saved tenant when omitted. Changing that tenant,
including adding a tenant to an initially unscoped conversation, requires a new
conversation. Other metadata filters remain specific to each request.

Tenant authorization for query, report, feedback, and ingestion resources is
still unfinished. Callers can select their request tenant; unfiltered single-turn
queries cover the full dataset. Conversation ownership alone does not provide
complete tenant authorization.

## Custom extensions and file access

- Custom `Retriever` and `VectorStore` search implementations accept
  `filters: MetadataFilters | None` and apply filters before candidate limits.
- Custom `Tool.build_payload` overrides accept the keyword-only
  `filters: MetadataFilters | None = None` argument. Direct dataset-tool callers
  supply metadata constraints in the nested `filters` input field.
- API ingestion reads CSV files under the configured data directory, and API
  index paths stay under the configured index directory. Move inputs into these
  directories before submitting requests that previously used arbitrary paths.

## MLflow tracking

The existing `mlflow` extra installs `mlflow-skinny`, SQLAlchemy, and Alembic.
Local SQLite tracking and logging to an existing remote server are supported.
Host the MLflow server/UI in a separate environment with its own dependencies.

For new local experiment configurations, use:

```yaml
tracking_provider: mlflow
tracking_uri: sqlite:///.artifacts/mlflow.db
```

MLflow 3.17 requires `MLFLOW_ALLOW_FILE_STORE=true` to continue using a legacy
`file:` tracking URI. Existing tracking history is not migrated automatically;
follow the [upstream migration guide](https://mlflow.org/docs/latest/self-hosting/migrate-from-file-store/)
when moving it to SQLite.
